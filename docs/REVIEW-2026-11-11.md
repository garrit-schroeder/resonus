## How to work with this report (agent protocol)

1. **Never delete or restructure before verifying.** Run the item's `Verify`
   command first; if the output contradicts the claim, stop and report — do not
   "adapt" the claim to the finding.
2. One work package (WP) = one focused change, landed and checked before the
   next. Items marked `⚠ BEHAVIOR` change runtime behavior and need extra care + tests.
3. After **every** WP run the full check suite, no regression allowed — measured

4. Never touch anything in the **Do-not-touch guard list** (Part 3 §G) — several
   apparent-dead items have dynamic consumers and deleting them breaks the build.
5. Where an item says "maintainer decision", answer it before editing and record
   the decision in the commit message.
6. **Code changes always go on a new branch, never on `main` and never on the
   branch this report sits on.** One branch = one feature or one bug fix: a branch
   carries one work package and nothing else, so a reviewer can say no to it alone.
   Two changes that belong together (the same question in two files, the same
   defect in two databases) still get **one branch each** — they do not share a
   branch just because they are alike; cross-branch grouping belongs in the
   pull request description, not in the branch.
   One carve-out, recorded rather than buried: when the person asks for a group of
   changes to share a branch, they do share it — and the verdict says so, naming what
   would otherwise have been a branch of its own, so a reviewer who reads one branch
   can still find the other half.
7. **Never create, update or merge a pull request, and never push to `main`.**
   Landing stops at the pushed branch: `git push origin <branch>`. Opening the
   pull request is the user's, manually and explicitly — an agent hands over the
   branch and the `gh pr create …` line for them to run, and stops there. One carve-out, recorded rather
   than buried: when the user instructs it in the conversation the pull request was opened here as well
   (#339, #341) — the rule is that it never happens by itself, and the record says who asked. #340 is the
   case where nobody did. Same
   for merging: nothing merges itself, not into `main`, not into this report's
   branch. A fix branch is therefore never merged into the branch carrying the
   report: the verdicts below record what landed where, the code does not come to
   this branch.

   **Where a pull request does get opened — by the user, on their own explicit
   request — it is opened against the upstream repo**, never against the fork:
   `gh pr create --repo juananzzz/resonus --base main --head 'garrit-schroeder:<branch>'`,
   which is exactly the flow `CONTRIBUTING.md:204-219` prescribes (branch → push to
   your fork → "open a Pull Request against `main` of `juananzzz/resonus`"). The fork
   (`origin`) is a **push target only**: a branch lives there so upstream can see it,
   and a review against the fork would review a repository nobody reads. The same two
   rules hold for **issues**: never open one yourself, and when the user asks for one
   it goes to `juananzzz/resonus` as well — hand over the
   `gh issue create --repo juananzzz/resonus …` line, run nothing.
8. Branch discipline that was measured to work on this repo (recorded so the next
   round does not rediscover it): the report's `src/` is the **pre-fix** tree, so
   each work package gets its own `git worktree` checked out straight off the
   baseline commit — a branch can only be checked out in one worktree at a time,
   and a worktree cannot be moved across filesystems (`/tmp` is one), so it is
   created at the right path from the start. A worktree has no dependencies of
   its own and the checks cannot run without them: symlink the main checkout's
   `node_modules` into it and never `git add` it (`git add src` / `git add docs`
   only, `git status` will keep showing `?? node_modules`).

   ```
   git worktree add -q <path> -b fix/<what-it-does> <baseline-commit>
   ln -sfn <main-checkout>/node_modules <path>/node_modules
   … commit …
   git push origin fix/<what-it-does>        # stop here. no pull request.
   ```
9. **A package the user rejects is withdrawn — everywhere — and its item goes back to
   open.** A pushed branch can be refused before anyone reviews it. Then all three
   copies go: unlink the worktree's `node_modules` symlink first and `git worktree
   remove <path>` (never `rm -rf` a worktree — that is how the real `node_modules`
   gets reached), `git branch -D fix/…`, and `git push origin --delete fix/…` so the
   fork stops showing a change nobody accepted. The verdict is then rewritten as
   **NOT LANDED**: a FIXED verdict may only name a branch that still exists, so any
   later round must `git branch`/`gh api` that branch before trusting the verdict. The
   finding itself is not re-reported — what the attempt learned (the shape that fits,
   the constants it argued, what had no test seam) stays in that verdict as a record
   of the attempt, not as a claim about the code, and a second attempt re-argues
   rather than copies.
10. **A fix that depends on whether an upstream API supports a field is settled by that API's own
   documentation, never by the client's behaviour** (recorded 2026-11-12, when the person asked for
   the official specification rather than an inference). A request that succeeds while quietly
   missing a field is indistinguishable from one that did the work — the screen can even answer
   "updated" — so behaviour cannot tell them apart. Read the published specification and quote the
   model's field list, plus the document's version, into the verdict; where a per-version document
   is not published under the name the docs build, say so instead of assuming the version the client
   supports. When the server has no such field at any door, the bug is the **affordance**: a row a
   person can type into and be told saved. The honest fix removes the row — the codebase's own idiom
   for "this source has no field for it" (`hidePublic`, the rating bar hidden per server type) — and
   leaves the field out of the edit, so nothing is queued for replay into a door that cannot take it.
11. **An observation is credited to whoever made it, and the record keeps the kinds of evidence apart**
   (recorded 2026-11-12, when a manual run against a real Jellyfin server on an Android emulator
   superseded a verdict that said "not tested on a device"). "Not tested" is a claim about **the agent's
   own reach**, never a fact about the app: when the reporter verifies a change by hand, that sentence is
   **superseded, not silently dropped** — write which part was measured where (the check suite the agent
   ran on the branch · the on-screen behaviour the reporter confirmed on the device · the endpoint facts
   from the published spec). Never fold a human's run into the agent's test counts, and never infer what
   their test covered: itemise only the observations they stated, as claims of that test.

12. **When upstream's `main` moves, bring the fork's local `main` across and re-measure before
   working anything** (recorded 2026-11-12, when the person merged the report's own pull requests
   upstream and had GitHub sync the fork). `git fetch upstream`, `git fetch origin`, then **`git
   merge --ff-only origin/main`** in the main checkout — *fast-forward only*, so a moved `main` can
   never paper over a commit that was supposed to live on a branch; if it does not fast-forward,
   stop and say so. Then re-measure in this order: the **whole check suite** on the new head first
   (a moved `main` may have moved the bar — the new numbers are the bar from here on), and every
   still-open item's **own `Verify:` as written**. Record the answers in a dated re-run section
   rather than rewriting the items around them: an item whose fix is now **merged** stops being
   owed and its "open, not merged" sentence is corrected in place, an item whose anchors moved gets
   the new ones, and a claim that no longer reproduces is written as a **correction**, never adapted
   to fit. A branch cut off the **old** head is stale: when the files it touched were also touched
   upstream, its pull request reads `CONFLICTING`/`DIRTY`, and re-cutting it off the new head
   re-opens a landing that was already recorded — so measure the overlap file by file, name what
   has to be re-derived, and let the re-cut itself wait for an explicit instruction. None of this
   moves the report's own branch, which stays baseline-plus-documents.
